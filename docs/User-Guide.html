1. About this guide

1.1 Purpose & scope

This document is a practical user guide for the Gadaa Istar Export E-Commerce Platform. It describes how the deployed system at gedaaistar.et and the back-office at admin.gedaaistar.et are used in practice by end-users and staff.

The guide covers every user-facing feature that a customer or an administrator can reach through the browser. It does not cover developer topics such as source-code layout, deployment pipelines, or infrastructure configuration — those live in the developer README.md and the internal engineering plan.

A dedicated appendix at the end (Appendix A) enumerates common misuse scenarios and user-related risks that follow from the workflows described earlier. That appendix is intended to feed the platform's risk register and privacy / security review.

1.2 Intended audience

  • Retail (B2C) customers browsing gedaaistar.et and placing personal orders.
  • Wholesale (B2B) buyers from businesses that hold an approved account and use tiered pricing and quote requests.
  • Customer-service staff and fulfilment staff using the admin back-office to manage orders, quotes, refunds, and customers.
  • Catalog managers and marketing staff managing products, pricing, coupons, and CMS content.
  • Super-administrators managing admin accounts, MFA, and system-level controls.
  • Auditors and risk / compliance reviewers using the misuse-scenarios appendix.

1.3 Conventions used

  • Monospace is used for URLs, file names, field values, and error codes.
  • Enter and other keys are shown in a boxed style.
  • Verbatim UI text is written in "quotes" to match the button or label the user actually sees.
  • Callout boxes appear throughout:
    • Tip — navy border, non-critical usage hints.
    • Warning — red border, actions with wider impact.
    • Risk — dark-red border, misuse and abuse indicators.
  • Storefront routes are shown as paths under gedaaistar.et (e.g. /checkout). Admin routes are shown as paths under admin.gedaaistar.et (e.g. /orders).

2. Platform overview

2.1 What Gadaa Istar sells

Gadaa Istar is a hybrid B2B + B2C export platform for Ethiopian coffee (raw and processed) and specialty agricultural products. The catalog is organised into seven categories:

  • Raw Green Coffee
  • Roasted Coffee
  • White Products (e.g. white sesame, pulses)
  • Spicy Products (chili, spices)
  • Oil Seed
  • Livestock
  • Mining

2.2 User roles

The platform recognises the following user categories:

Role Where they log in What they can do
Guest visitor — (no login) Browse catalog, add to cart, add to wishlist, look up an order using invoice + email.
B2C customer
"Retail" (RETAIL group)		 gedaaistar.et » Sign in Everything a guest can do, plus place orders, save addresses, view order history.
B2B customer
Wholesale (WHOLESALE_T1, WHOLESALE_T2, VIP)		 gedaaistar.et » Sign in (after admin approval) Everything a B2C customer can do, plus request quotes, buy at tiered wholesale prices with MOQ multipliers.
ADMIN
Back-office staff		 admin.gedaaistar.et Manage products, orders, quotes, customers, price lists, shipping, coupons, CMS. Most read/write endpoints require this role.
SUPERADMIN admin.gedaaistar.et Everything an ADMIN can do, plus create / disable other admin accounts, reset another admin's MFA secret, and delete customer groups.

2.3 Application URLs

EnvironmentStorefrontAdmin
Production https://gedaaistar.et/ https://admin.gedaaistar.et/

2.4 Supported browsers & devices

The storefront is built as a modern responsive application (Angular with server-side rendering) and is intended to work on:

  • The latest two versions of Chrome, Edge, Firefox, and Safari.
  • Mobile Safari on iOS 15+ and Chrome on Android 11+.

The admin back-office is intended for desktop use in a modern browser. JavaScript and cookies (for session state) must be enabled. A stable internet connection is required.

2.5 Languages & currencies

The storefront supports three interface languages, selectable from the header:

  • English — default
  • Amharic (አማርኛ)
  • Afaan Oromoo

Prices can be displayed in USD (default for English) or ETB (default for Amharic / Afaan Oromoo). The user's choice is saved in the browser so it persists across visits.

Where preferences live Language, currency, wishlist contents, and the guest-cart session key are all stored in the browser's local storage. Clearing browser data will reset them.

Storefront user guide

How retail (B2C) shoppers and wholesale (B2B) buyers use gedaaistar.et — from first visit to placed order to quote negotiation.

3. Storefront — getting started

3.1 Global navigation

Every page on the storefront shares the same header and footer.

Header

  • Brand block: Gadaa Istar logo, wordmark, and the tagline "Business Group S.C.". Clicking it returns to the home page.
  • Search box: "Search products…". Pressing Enter submits and routes to /shop?q=….
  • Language switcher: dropdown with English (default), Amharic, and Afaan Oromoo.
  • Currency toggle: two buttons, USD and ETB.
  • Sign in / Sign up buttons when signed-out; a greeting chip ("Hi, name") and a "Sign out" button when signed-in.
  • Wishlist heart icon with a live count badge.
  • Cart icon with a live count badge.

Primary navigation bar

Under the header there is a row of category links (Raw Coffee, Roasted Coffee, White Products, Spicy Products, Oil Seed, Livestock, Mining) plus Our Story (/about), Contact Us (/contact), and Track Order (/track-order).

Footer

  • Column 1 — Gadaa Istar: short description and motto "We are in you, you are in us."
  • Column 2 — Shop: the seven category links.
  • Column 3 — Company: About, Contact, Track Order, Wishlist, FAQ, and any published CMS pages.
  • Column 4 — Legal: Terms of Service, Privacy Policy, Shipping & Returns.
  • Bottom bar: copyright, "All rights reserved.", and card-scheme badges (VISA, MASTERCARD, AMEX, JCB).
Tip — keyboard-friendly search You can search from anywhere on the site by clicking the search box at the top and typing a keyword; press Enter to open the shop with that filter applied.

4. Home page

URL: /

The home page opens with the following blocks (top to bottom):

  1. Marketing banners. A rotating strip of banners maintained by the marketing team through the admin back-office. Each banner is optionally clickable.
  2. Hero section. Fixed content:
    • Eyebrow: "Direct from origin · Ethiopia"
    • Headline: "From Ethiopian highlands to the world's table."
    • Two calls to action: "Explore products" (opens /shop/raw-coffee) and "Contact & export inquiries" (opens /contact).
    • Trust badges: Organic-ready, Fairtrade-friendly, PCI DSS secure checkout, Multi-currency (USD · EUR · GBP).
  3. Stats strip. Static facts: 7 product categories, 100% traceable origin, 30+ destination countries, Addis Ababa quality-check facility.
  4. Featured products carousel. Auto-advances every 5 seconds. Each card shows an image, name, short description, price, and an "In stock" or "Sold out" badge. A "View all" link opens the full catalog.
  5. Category tiles. Seven clickable tiles — one per category — that jump to /shop/<category>.
  6. Trust section. Four reassurance blocks: PCI DSS SAQ A payments, global shipping (DHL & FedEx retail), VAT-compliant invoicing, and B2B / B2C accounts.

5. Browsing the catalog

URL: /shop or /shop/<category>

5.1 Filtering and searching

  • The search bar at the top of the shop is debounced — typing pauses for 300 ms before the results refresh.
  • An X button clears the current search.
  • The category rail below the header lets you switch between All and any of the seven categories.
  • The URL updates as you filter, so the filtered page is bookmarkable and shareable.

5.2 The product grid

Each card in the grid shows:

  • Primary product image (or a placeholder icon).
  • Category label.
  • Product name.
  • Short description.
  • Price. A strikethrough original price is shown when a discount applies, along with a "Save X%" badge.
  • An "Out of stock" badge if the item is unavailable.

The grid paginates 12 items at a time. "Previous" and "Next" buttons and a "Page X of Y" indicator sit under the grid.

Empty results If no products match, the shop shows either "No results found" (when a search term is active) or "No products yet" (for an empty category). If the API cannot be reached, the shop shows "Could not load the catalog. Please try again." with a retry button.

6. Product details

URL: /products/<slug>

6.1 Layout

  1. Breadcrumb: Home » Shop » Category » Product name.
  2. Media gallery: a hero image plus a thumbnail strip. Sale and Out-of-stock badges overlay the hero.
  3. Product info: category, name, short description, and the resolved price (with strikethrough if a discount / tier price applies).
  4. Variant selector: a radio list of variants, each showing its attributes, stock ("X available" or "Out of stock"), and price override if different.
  5. Product facts: origin country (displayed as "Ethiopia" when the ISO code is ET), unit weight, HS code, and minimum order quantity.
  6. Quantity + Add to cart panel.
  7. Wholesale price ladder — for B2B accounts only. A table of "Order at least" and "Unit price".
  8. About this product: full description.
  9. Packaging: packaging notes if the product ships in a specific pack.

6.2 Adding to cart

  1. If the product has variants, choose one first. If you don't, the site shows: "Please select a variant first."
  2. Adjust the quantity with the − and + buttons. The minimum is set by the product's minimum order quantity (MOQ), and B2B customers may see a larger effective MOQ because of their group multiplier.
  3. Click Add to cart. While the request is in flight the button shows "Adding…". A green confirmation flash "Added to cart" appears for 3 seconds.
  4. The heart icon at the top-right of the panel toggles the product in your wishlist.
Server-side validation Backend errors are shown verbatim: INSUFFICIENT_STOCK (someone else bought the last units first), MIN_ORDER_QUANTITY (quantity below the effective MOQ), or PRODUCT_NOT_PURCHASABLE (draft or archived product). Adjust the quantity or variant and try again.

7. Wishlist

URL: /wishlist

The wishlist is a purely client-side feature that stores product slugs in your browser's local storage. It works without signing in and persists across visits on the same browser.

7.1 What you see

  • Header: "Your wishlist" with an item count.
  • Product cards showing the image, name, SKU, price, an "Out of stock" badge when applicable, an Add to cart button (disabled if out of stock), and a remove-heart button.
  • If a saved item has been removed from the catalog, the card is replaced with "Product unavailable" and a "Remove" button.
  • Empty state: "No saved items yet. Tap the heart icon on any product to save it for later."
The wishlist does not sync between devices Wishlists live only in the local browser. Signing in does not migrate them, and clearing browser data will empty the wishlist.

8. Shopping cart

URL: /cart

8.1 Cart contents

Each line in the cart shows:

  • Product thumbnail and name (link back to the product page).
  • Variant name and SKU.
  • Unit price. When the storefront detects that the catalog price has changed since the item was added, a "Price updated" note appears.
  • An "Only X in stock" warning if the requested quantity exceeds available stock.
  • A quantity stepper (− and +) and a live line total.
  • A Remove button.

8.2 Order summary

  • Item count (number of SKUs and total units).
  • Subtotal.
  • Tax and Shipping shown as "Calculated at checkout".
  • Proceed to checkout button. If the user is a guest, this redirects to /login?next=/checkout.
  • Request a quote button — visible only if the user is signed in and the cart is non-empty. Recommended for B2B buyers who want to negotiate.
  • The reassurance line "Secure payment via CyberSource".

8.3 Empty cart

An empty cart shows a friendly empty state and a link back to the catalog. Clicking "Empty cart" asks for confirmation before removing everything.

Guest carts are preserved on sign-in When a guest signs in or registers, any items already in the guest cart are merged into the customer's cart automatically. The guest session key lives in local storage under gi-guest-session-key.

10. Email verification

10.1 "Check your inbox" page

URL: /verify-email/pending

After registration, the storefront shows the "Check your inbox" page: "We've sent a confirmation link to your email. Click it to activate your account. The link expires in 60 minutes." Two actions are available: Resend the email and Back to home.

Clicking the link from the email opens a page that goes through three states:

11. Signing in and out

11.1 Sign in

URL: /login

  • Fields: Email (required, valid format), Password (required, min 8 characters).
  • Button: "Sign in". While loading it shows "Signing in…".
  • Links: "Forgot your password?" and "New to Gadaa Istar? Create an account".
  • If the URL contains ?reset=1 or ?passwordChanged=1, a green banner confirms the earlier action.
  • Error messages are explicit: "The email or password you entered is incorrect.", "Your account has been suspended. Please contact support.", "Your B2B account is still awaiting approval.", "Could not reach the server. Please check your connection."
  • On success the browser is redirected to ?next= (if present) or /account.

11.2 Sign out

Click "Sign out" in the top bar. This clears the session on the server (revokes tokens) and locally. You are returned to the home page.

Changing a password signs out every device Using the "Change password" flow (below) invalidates every active session on every browser and device you are signed in on.

12. Recovering your password

12.1 Forgot password

URL: /forgot-password

Enter the email address on your account and click Email me a reset link. The screen always shows the same reassurance message ("If email matches an account, we've just sent a reset link. It's valid for the next 30 minutes.") whether or not the address is on file — this prevents enumeration of registered emails.

12.2 Reset password

URL: /reset-password/<token>

  • Enter and confirm a new password (8–128 characters).
  • Click Save new password.
  • On success you see "Password updated" and after 2.5 seconds you are redirected to /login?reset=1. All other sessions have been revoked.
  • Errors: "Password must be 8–128 characters.", "Both passwords must match.", "That reset link is invalid or has already been used. Request a new one.", "That reset link is no longer valid — request a new one."

14. Checkout & payment

URL: /checkout (sign-in required)

Checkout is a single page composed of five stacked panels. Every step keeps its state as the user scrolls up and down.

14.1 Ship to

  • Saved addresses appear as radio-selectable cards. The default address is preselected.
  • A Default badge marks the current default.
  • Clicking Add a new address opens the inline address form (same field set as in Section 13.2).
  • Country code is validated: "Use a 2-letter code, e.g. ET, US, DE."

14.2 Shipping method

  • While shipping options load: "Calculating shipping options for your cart…".
  • Once loaded, each option shows its name, description, ETA ("min–max business days"), and cost.
  • The current weight the price is based on is shown as "Priced for your cart (X kg)".
  • If no options exist for the destination, checkout still allows placement but shipping is billed at zero.

14.3 Coupon code

  • Enter a code (max 64 characters) and click Apply.
  • An applied coupon shows the code, description, discount (percentage or amount), and any "free shipping" flag. A Remove button clears it.
  • The discount preview line updates immediately on the summary.

14.4 Payment method

A radio list of payment methods offered by the platform. The default is Mastercard Payment Gateway (MPGS). Each option shows a name and a short description.

14.5 Notes

An optional free-text field (max 1000 characters) for the fulfilment team.

14.6 Order summary and placement

The right-hand summary shows every cart line with thumbnails, quantities and prices, and the running totals: Subtotal, Tax ("Applied at payment"), Shipping (with method name), Discount (with the coupon code), and an estimated total. The button reads Continue to secure payment. Underneath the button: "You'll be redirected to Mastercard / CyberSource".

What happens when you click "Continue to secure payment" The platform creates the order in Pending payment status and submits an auto-post form that hands the browser to CyberSource or MPGS. Card details are entered on the payment processor's page — the storefront never receives them. This is what makes the platform PCI DSS SAQ-A compliant.

15. After payment

15.1 "Payment confirmed" page

URL: /checkout/return

Depending on the gateway's response the page shows one of several states:

  • Loading: "Finalising your payment…".
  • Pending: "Waiting for your bank to confirm…". The page automatically re-checks the order status every 3 seconds for up to 30 seconds.
  • Success: "Thank you — your order is confirmed!" with the invoice number, status, total, and paid date. Two actions: View order details and Keep shopping.
  • Cancelled: "Payment didn't go through" — order cancelled, no charge.

15.2 "Payment cancelled" page

URL: /checkout/cancel

  • If the order is still Pending payment the page shows "Payment paused" with two buttons: Retry payment (auto-posts to the gateway again) and Cancel this order (asks for confirmation, releases the reserved stock).
  • If the order is already Cancelled the page shows "Order cancelled" and offers Keep shopping or View order.

16. Requesting a quote (B2B)

Wholesale buyers can turn their cart into a quote request instead of placing an order.

  1. Add products to the cart the normal way, respecting the tier's MOQ multiplier.
  2. Open /cart.
  3. Click Request a quote in the summary panel. The button is only visible if you are signed in and the cart is non-empty.
  4. You are redirected to the new quote's detail page under /account/quotes/<uuid>. The quote is now in SUBMITTED status; the sales team is notified.
  5. Later, the customer returns to /account/quotes, opens the quote once the status is SENT, reviews the proposed pricing and validity, and clicks Accept quote. The sales team then converts the accepted quote into a live order (paid separately).
Quote lifecycle at a glance DRAFT → SUBMITTED → UNDER_REVIEW → SENT → ACCEPTED → CONVERTED. A quote can be REJECTED from SUBMITTED or UNDER_REVIEW, or EXPIRED if it passes its validity window.

17. Tracking an order (public)

URL: /track-order

Any visitor — signed in or not — can look up an order:

  1. Enter the order reference (e.g. GI-2026-00003) or its UUID.
  2. Enter the email that was used at checkout.
  3. Click Track order.

When the email matches the order the page reveals the invoice, placed and paid timestamps, shipping method, item list, grand total, and a status history. If nothing matches, the friendly message "No matching order found. Check that the order reference and email are correct. If you placed the order as a guest, use the email you entered at checkout." is shown.

Risk — enumeration attempts Because the tracking endpoint accepts any invoice number, malicious users may attempt to guess order references. The platform only reveals order details when both the reference and the correct email are supplied, so no confidential information leaks — but repeated failed lookups may still indicate scraping and should be monitored via server logs.

18. Static pages

URL: /pages/<slug> (shortcuts: /about, /contact)

Content pages such as About Us, Contact, FAQ, Terms of Service, Privacy Policy, and Shipping & Returns are managed as CMS entries in the back-office. If a slug does not resolve, the page shows "Page not found." with a "Back to home" link.

Part II

Admin back-office user guide

How back-office staff use admin.gedaaistar.et — sign-in, catalog management, order and quote handling, customer approvals, coupons, CMS content, and admin user administration.

19. Signing in to the back-office

URL: https://admin.gedaaistar.et/login

Every admin session begins with a two-step sign-in:

  1. Email and password on the login page.
  2. A time-based one-time code (TOTP) on the MFA page.

19.1 Login

  • Fields: Email (required), Password (required, min 8, show/hide toggle).
  • Helper text: "You'll be asked for a 6-digit code from your authenticator app after this step."
  • Button: "Continue" (shows "Signing in…" while loading).
  • Link: "Forgot password?"

Common error messages:

  • "That email or password is incorrect. Please try again."
  • "This admin account is disabled. Contact a super-admin."
  • "Please check the highlighted fields and try again."

19.2 Multi-factor authentication (MFA)

URL: /verify-mfa

First sign-in — enrolment

The first time an admin signs in, the page shows:

  • Heading: "Set up two-factor authentication".
  • Explanation: "This is your first sign-in as email. Scan the QR code below with an authenticator app (Google Authenticator, Authy, 1Password, …), then enter the 6-digit code to finish."
  • A 220×220 px QR code generated client-side.
  • An "Or enter the code manually:" block with the Base32 secret, issuer, and account name.
  • Algorithm info: "SHA-1 · 6 digits · 30-second window".
  • Input: "Authentication code" (6 digits).
  • Buttons: Finish setup and Cancel and sign in again.

Returning sign-ins

  • Heading: "Enter your 6-digit code".

25.4 Refunds

  • Refund amount — pre-filled with the remaining refundable balance.
  • Reason — required, minimum 3 characters ("Please provide a reason (3+ chars) — it goes on the audit log.").
  • Manual refund — checkbox that bypasses the payment gateway (only used when the money was already refunded out-of-band, e.g. by bank transfer).
  • Issue refund — runs the refund; on success the message reads "Refunded amount — gateway." On gateway failure: "Refund attempt recorded, but the gateway rejected it: error."
Risk — manual refunds "Manual refund (bypass gateway)" is powerful and must be reserved for reconciled, out-of-band refunds. It writes to the audit log but does not move any real money on its own.

Misuse scenarios & user-related risks

A short catalogue of misuse patterns that follow from the workflows described in this guide, with the controls the platform already provides and the operational guidance staff should follow.

Appendix A — Misuse scenarios & user-related risks

This appendix summarises the most relevant misuse scenarios and user-related risks for the Gadaa Istar platform. It is intentionally kept short and is designed to feed the platform's risk register and the periodic security & compliance review. Each row lists the actor, the scenario, the potential impact, and the controls / mitigations that are either already in place or should be enforced operationally.

A.1 Storefront (customer-facing) risks

Actor Scenario Impact Controls / mitigations
Guest / attacker Account-enumeration via login, forgot-password, or registration forms. Discovery of registered email addresses (privacy leak). Login errors are generic ("The email or password you entered is incorrect."). Forgot-password always returns success. Registration returns "already exists" — rate-limiting and reCAPTCHA recommended if abuse is observed.
Guest / attacker Credential-stuffing against /login. Account takeover. 8-character password minimum, per-account rate-limiting server-side, MFA on admin side only. Operational: monitor bulk 401 responses and enable IP-level throttling.
Guest / attacker Order-reference enumeration on /track-order. Attempted disclosure of order details. Lookup requires both invoice number and matching email. Monitor failed lookups by IP.
Customer Repeatedly abandoning checkouts to lock stock ("stock hoarding"). Legitimate buyers see items as unavailable; false low-stock alerts. Reservations are released on order cancellation. Dashboard exposes "Abandoned orders" (> 1 hour) for review.
Customer Coupon-code brute force at checkout. Discovery of active promotional codes. Coupon "Max redemptions" and "Max per customer" caps enforce natural limits. Consider rate-limiting apply-coupon calls at the gateway level.
B2C customer posing as B2B Registering as a business with false company data to obtain wholesale pricing. Revenue loss; misrepresentation. B2B accounts start in Pending B2B approval and cannot buy at tier prices until an admin verifies the business licence out-of-band before clicking Approve B2B.
Customer Chargeback fraud — disputing a legitimate paid order. Financial loss; card-scheme penalties. Payment is processed by CyberSource / MPGS (PCI DSS SAQ-A). Order status timeline, IP and address records feed dispute responses; use refund panel's Manual refund only when the money has already moved out-of-band.
Customer Sharing a single account between many buyers of the same company. Weak accountability; wholesale abuse. Discourage in onboarding. Address book & order history are per-account. Session revoke on password change enforces re-authentication.
Attacker with a stolen token Reusing a leaked password-reset or verify-email link. Account takeover. Reset links expire in 30 minutes and are single-use; verification links expire in 60 minutes. Using a reset revokes all sessions.
Customer Weak, reused, or shared password. Account takeover. 8–128 character range enforced. Recommend adding password-breach checking and a strong-password policy in a future release.
Attacker (XSS) Injecting HTML through free-text fields such as address, notes, or profile. Session hijack; defacement. Angular auto-escapes template bindings; CMS body HTML is sanitised. Do not disable sanitisation. Review any admin-authored CMS body before publishing.
Guest Shared / public device leaves an active session behind. Account takeover on the same device. Session stored in localStorage. Encourage users to sign out on shared devices; password change revokes all sessions.

A.2 Back-office (admin-facing) risks

Actor Scenario Impact Controls / mitigations
Malicious insider Approving a fraudulent B2B account without verifying the licence. Revenue loss; opens the door for wholesale-price fraud. The "Approve B2B" confirmation reminds staff to verify the business licence out-of-band. Every approval is written to the audit log with the actor identity.
Malicious insider Issuing "Manual refund (bypass gateway)" without the money actually moving. Direct financial loss. Reason required (min 3 chars) and audit-logged. Restrict Refund permission to trusted roles. Reconcile refunds daily against gateway statements.
Malicious insider Editing prices, coupons, or shipping costs to favour a specific buyer. Revenue leakage. Historical orders keep the price snapshot at placement time. All price / coupon / shipping-method changes are audit-logged.
Malicious insider Force-verifying a customer email without confirmation. Account takeover of that customer email. Explicit confirmation dialog and audit-log entry per action. Restrict the customer-detail write actions to authorised staff.
SUPERADMIN abusing MFA reset Resetting another admin's MFA to impersonate them. Full compromise of a peer admin account. Only SUPERADMIN can reset another admin. Every reset is audit-logged and revokes the target's sessions immediately. Require two-person approval for MFA reset operationally.
Attacker Phishing an admin's password + TOTP in real time. Full back-office access. MFA (SHA-1, 6 digits, 30 s window) mitigates static-password theft. Recommend FIDO2 for the future. Train staff to visit admin.gedaaistar.et directly (never via email links).
Attacker Shoulder-surfing or session theft on shared workstations. Order tampering, customer-data exposure. Sign-out button in the top bar; every write operation is audit-logged. Enforce workstation lock policies operationally.
Admin Publishing CMS Body HTML that contains third-party trackers or invisible content. Legal risk (privacy), brand risk. Body HTML is sanitised on the storefront but not stripped of tracking pixels; peer-review any CMS change before publishing.
Terminated employee Continued admin access after termination. Data exfiltration, order tampering. Deactivate the admin user promptly (Admin users screen). Session tokens can be revoked out-of-band by resetting MFA.

A.3 Operational recommendations

  1. Enable server-side rate-limiting on /login, /forgot-password, /track-order, /coupons/apply, and the guest cart endpoints.
  2. Alert on any burst of failed MFA_INVALID_CODE or INVALID_CREDENTIALS errors from a single IP or account.
  3. Require two-person approval for any Reset MFA, Force verify email, or Manual refund action — operationally, not just technically.
  4. Review admin audit logs weekly for out-of-hours activity, refunds, price changes, and CMS publishing.
  5. Reconcile refunds daily against the CyberSource / MPGS statements.
  6. Provide staff with dedicated MFA devices and never share TOTP secrets.
  7. Roll out password-breach checking and stronger password policy on the storefront in a future release.
  8. Encourage retail customers to sign out on shared devices; consider a session-timeout banner.
