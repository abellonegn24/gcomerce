Backend
-------
- Refactor: extracted shared web/security infra to new `web-common` module

- JwtIssuer extended with `issueShortLivedToken()` + `verifyPurpose()` —
  the JOSE `typ` header carries a purpose label ("mfa-challenge", "email-
  verify", ...) so short-lived tokens can't be replayed across flows.
- SecurityContextHolder gained `requireAnyRole(String...)` for RBAC.

- Flyway V3 migration: `admin_refresh_token` table + `mfa_enrolled_at`
  column on `admin_user`. Seeds a bootstrap super-admin
  (admin@gadaaistar.com / ChangeMe-Admin-2026!) with MFA not yet enrolled.

- Persistence: `AdminRefreshToken` entity + `AdminRefreshTokenRepository`.
  `AdminUser` gained `mfaEnrolledAt` and `isMfaEnrolled()`.

- New Gradle module `api-admin` (Quarkus runtime on port 8081, own
  application.properties, own SystemResource /hello).
  * `TotpService` — self-contained RFC 6238 implementation (30s step,
    6-digit code, HMAC-SHA1, base32 secret with local RFC 4648 codec, no
    dependency added). Builds Google-Authenticator-compatible
    `otpauth://totp/...` provisioning URIs.
  * `AdminRefreshTokenService` — rotation + reuse-detection, parallel to
    the storefront's `RefreshTokenService` but coupled to AdminUser.
  * `AdminAuthService` implements the two-step MFA flow:
      1. POST /login    → returns short-lived challenge JWT + state
         (MFA_REQUIRED or MFA_ENROLLMENT_REQUIRED with provisioning URI).
      2. POST /verify-mfa → verifies challenge JWT + TOTP code, sets
         mfa_enrolled_at on first success, issues access+refresh tokens.
  * `AdminAuthResource` under /api/admin/v1/auth: login / verify-mfa /
    refresh / logout / me.

- Docker: parameterized backend Dockerfile via `--build-arg MODULE=<name>`
  + PORT; docker-compose now builds two backend services (api-storefront
  on 8080, api-admin on 8081) from the same Dockerfile.

Backend rate limiting
---------------------
- common/exceptions/RateLimitExceededException — extends ApiException, HTTP 429,
  carries retryAfterSeconds; encoded into the standard error envelope so
  clients can key off code=RATE_LIMIT_EXCEEDED.
- api-storefront/ratelimit/RateLimit — @Retention(RUNTIME), targets METHOD +
  TYPE. Fields: bucket, max, windowSeconds. Purely metadata — no @NameBinding.
- api-storefront/ratelimit/RateLimitService — in-memory sliding-window store
  keyed by "bucket|clientId". ConcurrentHashMap<String, ArrayDeque<Long>>;
  per-queue synchronized to keep pruning + insert atomic. Config knobs:
  gadaa.ratelimit.enabled + gadaa.ratelimit.max-queue-size. @Scheduled every 5m
  reaps queues idle for 15+ minutes. Returns Decision(allowed, retryAfterSeconds).
- api-storefront/ratelimit/RateLimitFilter — @Provider ContainerRequestFilter
  at Priorities.AUTHENTICATION - 100 (runs before JWT filter). Reads @RateLimit
  from the resource method or class via injected ResourceInfo. Derives client
  identity from X-Forwarded-For (first token), else X-Real-IP, else Vert.x
  socket remote address, else "unknown". On denial, throws
  RateLimitExceededException so GlobalExceptionMapper handles response shape.
- GlobalExceptionMapper — new branch for RateLimitExceededException that
  adds the standard `Retry-After: <seconds>` header. Refactored helper into
  BuiltResponse record so both the rate-limit path (with extra header) and
  the plain ApiException path share the envelope builder without duplication.
- AuthResource — @RateLimit annotations applied per-endpoint:
    POST /register              → bucket=auth-register,             5 / 10min
    POST /login                 → bucket=auth-login,                10 / 1min
    POST /resend-verification   → bucket=auth-resend-verification,   3 / 10min
    POST /forgot-password       → bucket=auth-forgot-password,       3 / 10min
    POST /reset-password        → bucket=auth-reset-password,       10 / 10min
    POST /me/change-password    → bucket=auth-change-password,       5 / 10min
- Configuration: gadaa.ratelimit.enabled (default true) + max-queue-size in
  application.properties; %test override disables the limiter so integration
  suites don't false-trip.

Backend profile management
--------------------------

  and ChangePasswordRequest (current + new, min 8).
- AuthService.updateProfile(id, req) — partial update; blank fields ignored

Backend — api-storefront cart API
---------------------------------
All under /api/storefront/v1/cart. Requires an authenticated customer.

- GET    /cart                          — get-or-create + fresh totals
- POST   /cart/items                    — add product; increments qty if line exists
- PATCH  /cart/items/{productId}        — overwrite qty; 0 quantity removes the line
- DELETE /cart/items/{productId}        — remove a single line
- DELETE /cart                          — empty the cart in one call

Every mutation is rate-limited under bucket cart-mutate at 60/min per IP.

Business rules enforced in CartService:
- Product must be ACTIVE (409 PRODUCT_NOT_PURCHASABLE otherwise).
- Requested qty must be ≥ product.min_order_quantity (400 MIN_ORDER_QUANTITY).
- Requested qty may not exceed inventory.quantity − inventory.reserved
  (409 INSUFFICIENT_STOCK).
- Cart currency locks to the first product's currency; mixing gets
  409 CURRENCY_MISMATCH.

Response shape (CartDtos.CartResponse) always includes:
- All lines with unit_price snapshot AND freshly-resolved current_unit_price,
  a boolean price_changed flag, and per-line stock status.
- Aggregates: distinctItems count, totalUnits (sum of qty across lines),
  subtotal (line snapshots — tax + shipping added in Phase 3b at checkout).

Price resolution mirrors StorefrontCatalogService: caller's group's active
price list ↦ entry with largest min_quantity ≤ requested qty; falls back
to product.basePrice. Duplicated in CartService for now; will be lifted
into a shared PriceResolver bean when Phase 3b's OrderService needs it.

Backend api-storefront — orders
-------------------------------
- OrderDtos: PlaceOrderRequest, CancelOrderRequest, OrderSummary (list row),
  OrderDetail (lines + status history + addresses inline).
- OrderMapper: injects AddressMapper so order detail carries full ship/bill
  address DTOs.
- OrderService.createFromCart — the checkout workhorse:
    validates cart is non-empty + owned addresses exist,
    re-resolves each line price via PriceResolver (cart snapshot is advisory),
    re-checks stock and RESERVES inventory (quantity untouched, reservedQuantity
      bumped) inside the same tx,
    applies TaxService for the ship-to country (15% ET, 0% zero-rated export),
    allocates a gap-free invoice number via InvoiceNumberService,
    snapshots product sku + name on each OrderItem,

  reservations and marks CANCELLED with a status event.

  @TxType.MANDATORY so it can only run inside an existing tx.
- OrderService.markPaid(order, txRef, provider) — called by the webhook:
  reservedQuantity − qty AND quantity − qty (converts reservation into a real
  decrement), sets paymentReference / paymentProvider / paidAt, transitions
  to PAID via the state machine.
- OrderService.markPaymentFailed(order, reason) — releases reservations,
  transitions to CANCELLED.

- OrderResource endpoints (all under /api/storefront/v1/me/orders):

    GET   /{uuid}/payment-payload  — signed CyberSource form fields
    POST  /{uuid}/cancel           — customer-initiated cancel

Backend api-storefront — CyberSource Secure Acceptance
------------------------------------------------------
- CyberSourceConfig — typed wrapper around gadaa.cybersource.* keys with
  isConfigured() gate so dev environments without real credentials fail
  fast with a 409 PAYMENT_GATEWAY_NOT_CONFIGURED envelope.
- CyberSourceService:
    buildRedirectPayload(order) — constructs the LinkedHashMap of form fields
      the browser POSTs to the hosted checkout page. Fields include access_key,
      profile_id, transaction_uuid, signed_date_time (ISO-UTC), locale,
      transaction_type=sale, reference_number=invoice_number, amount (2dp),
      currency, override_custom_receipt_page + override_custom_cancel_page
      pointing at /checkout/return + /checkout/cancel on the storefront URL,
      full bill_to_* block from the order's bill-to address.
    Signature: HMAC-SHA256 over "field1=value1,field2=value2,..." in the
      exact order declared in signed_field_names (which is itself signed).
      Base64-encoded output goes into the "signature" field.
    verifySignature(params) — constant-time comparison to defeat timing
      side-channels; used by the webhook.
- CyberSourceWebhookResource (public, JAX-RS @Consumes form-urlencoded):
    Verifies HMAC before any state mutation; failed verification returns 400
      with INVALID_SIGNATURE (no body echo — defensive).
    Looks up the order by req_reference_number (= invoice_number).
    Idempotency: if the order is no longer PENDING_PAYMENT we return
      { "status": "already_processed" } without re-mutating.
    Decision switch:
      ACCEPT           → orderService.markPaid(order, transaction_id, "CYBERSOURCE")
      DECLINE/CANCEL/ERROR → orderService.markPaymentFailed(order, reason)
      REVIEW / unknown → left in PENDING_PAYMENT for manual review, logs warn.

Design decision
---------------
We chose a **proxy upload** (browser → api-admin → MinIO) instead of
presigned POST URLs. Rationale: (1) no CORS surprises on the MinIO side,

Design decision — customer status state machine
-----------------------------------------------
Kept intentionally narrow. Admin-initiated transitions are limited to:
  PENDING_VERIFICATION  → DEACTIVATED
  PENDING_APPROVAL      → DEACTIVATED             (reject B2B application)
  ACTIVE                → SUSPENDED | DEACTIVATED
  SUSPENDED             → ACTIVE | DEACTIVATED
  DEACTIVATED           → (terminal — no exit)
Everything else must go through customer-facing flows:
  * PENDING_VERIFICATION → ACTIVE via the storefront email-verification link
    (or the admin's dedicated "verify-email" action for out-of-band cases).
  * PENDING_APPROVAL → ACTIVE via the dedicated "approve-b2b" action.
This keeps the audit trail clean — status changes have clear intent and can't
be used to smuggle around the licence-approval step.

Two independent items shipped in one phase because they close the two most

------------------------
Part 1 — Admin-initiated customer password reset
------------------------
Design choice — no cross-module refactor
The obvious approach would have been to move api-storefront's
PasswordResetService into web-common so both apps share it. That would
mean also relocating MailService (which owns Qute templates) and the
sha256Hex helper. Too much surface area for a single support tool.
Instead: duplicate the tiny reset primitive inside api-admin. It only
needs to (a) mint a token, (b) hash it identically to the storefront so
the storefront's *complete()* endpoint can consume it, (c) send the mail.
The token entity + repo already live in the persistence module — both
apps read/write the same rows.

Anti-enumeration silence removed
Storefront /forgot-password intentionally returns 200 for both known
and unknown emails (so callers can't harvest addresses). Admin path is
different: the caller is an authenticated admin whose intent is to
help a specific known customer. If the ID is bad, return 404 loudly
so the admin sees the misclick.

Side effects on success
  1. All previously-unused password_reset_token rows for this customer
     are marked usedAt=now — only the freshly-minted link is live.
  2. All customer_refresh_token rows for this customer are revoked
     (revokeAllForCustomer) — prevents an attacker holding a stolen
     access token from acting during the reset window.
  3. The templated HTML+text email is queued via Quarkus Mailer.
     Copy differs from the storefront template: it identifies the
     message as admin-initiated and adds "reply to your usual contact
     if you didn't expect this".

Backend api-admin
- resources/templates/mail/password-reset.{html,txt} NEW: copied +
  reworded from the storefront originals. Duplication is fine — the
  two flows have subtly different copy (storefront: "we received a
  request"; admin: "a support team member issued a reset link"). Same
  {displayName} / {resetLink} / {expiresMinutes} params so Qute
  contract matches.
- application.properties: two new keys —
    * gadaa.auth.admin-password-reset-ttl-minutes (default 60,
      double the storefront's 30 because admin issues links during
      business hours for customers who may be in a different tz)
    * gadaa.frontend.storefront-url (used to build the reset link —
      NOT the admin URL; the customer clicks through to the
      storefront to complete).
- infra/docker-compose.yml: STOREFRONT_BASE_URL and
  GADAA_ADMIN_PASSWORD_RESET_TTL_MINUTES env vars threaded through so
  the containerised admin service inherits them.
- customers/AdminCustomerResetService.java NEW: ApplicationScoped
  @Transactional bean.
    * start(customerId, actorId) → CustomersDtos.ActionResponse.
    * Uses HexFormat.of().formatHex(digest) — identical lowercase

Part 2 — Editing an existing price list
------------------------
Design choice — customer group is immutable
Retargeting a list from RETAIL to WHOLESALE_T1 would silently move
every entry to a group that wasn't intended to receive them. Almost
always a bug when it happens. The server enforces this by leaving
customerGroup off UpdatePriceListRequest entirely — no way to change
it via PATCH. If you truly need a different tier, delete + recreate.

Design choice — explicit clear flags for dates
{"effectiveFrom": null} is ambiguous in a PATCH: does the admin mean
"leave alone" or "wipe"? Solved by adding clearEffectiveFrom /
clearEffectiveTo booleans. Backend logic:
  - clearXxx=true       → set to null.
  - value present       → set to that value.
  - both null/false     → leave the existing value.
Frontend derives the flag by comparing the form's blank string to the
original row's populated value, so the admin never has to check a
box themselves.

Backend api-admin
- catalog/CatalogDtos.java: UpdatePriceListRequest record NEW —

- catalog/PriceListsResource.java: adds PATCH /{id} handler gated to

  catalog resources; Note: this is NOT CUSTOMER_MANAGER because price

- Flyway V7 migration `V7__order_refunds.sql`:
    - `order_refund(id, uuid, order_id, amount, reason, status,
      gateway_provider, gateway_reference, gateway_error_code,
      gateway_error_message, initiated_by_admin_id, created_at,
      updated_at)` with `UNIQUE(uuid)`, `INDEX(order_id, created_at)`,
      `INDEX(status)`. FK to checkout_order is ON DELETE RESTRICT
      (the audit log must survive), FK to admin_user is ON DELETE SET
      NULL (removing an admin user should not wipe history).

      denormalises the cumulative refund total so the admin list can
      render "40.00 / 100.00" without a JOIN.
- Persistence: `OrderRefund` entity + `Status` enum (PENDING /
  SUCCEEDED / FAILED) + `OrderRefundRepository` with `findByUuid`,
  `listForOrder`, and a `sumSucceededForOrder` sanity check.
  `CheckoutOrder` gained the `refundedTotal` column and a
  `List<OrderRefund> refunds` collection ordered oldest-first.
- api-admin `payment/CyberSourceRefundConfig`: typed wrapper over the
  CyberSource REST credentials (merchant-id, key-id, secret-key,
  host, timeout-seconds). Deliberately separate from the storefront
  Secure Acceptance config — the two APIs use different auth schemes
  and different credentials on the CyberSource side; conflating them
  would let ops paste a Secure Acceptance secret and think refunds
  would work. `isConfigured()` returns false when any credential is
  blank so the service layer can gracefully fall back to MANUAL.
- api-admin `payment/CyberSourceRefundClient`: JDK 11+ `HttpClient`
  wrapper around POST /pts/v2/payments/{captureId}/refunds. Auth uses
  the CyberSource "HTTP Signature v1" scheme: SHA-256 body digest,
  RFC-1123 date, HMAC-SHA256 signing string over
  `host / date / (request-target) / digest / v-c-merchant-id`, and a
  `Signature` header carrying keyid + algorithm + headers + signature.
  Base64-decodes the secret with a UTF-8 fallback so a mis-formatted
  secret produces a 401 (actionable) not a boot NPE. Returns a
  `RefundOutcome(success, refundId, errorCode, errorMessage)` record;
  timeouts and IO exceptions are captured as failure outcomes rather
  than propagated, so the caller can persist a FAILED row for the
  audit log.
- api-admin `refunds/RefundDtos`: `CreateRefundRequest(amount,
  reason, manual?)` with Jakarta Bean-Validation, and `RefundEntry`
  used by both the list endpoint and embedded in AdminOrderDetail.
- api-admin `refunds/RefundService`: the single @Transactional entry
  point. Validates the current status is refundable (rejects
  PENDING_PAYMENT / CANCELLED / already-REFUNDED with distinct error
  codes ORDER_NOT_REFUNDABLE / ORDER_FULLY_REFUNDED), validates the
  amount does not exceed grand_total − refunded_total
  (REFUND_EXCEEDS_REMAINING), calls the gateway when configured
  (skipping the call when the admin ticked "manual" or when creds are
  blank — either way the row is persisted with gateway_provider=

  order_refund row + updates order.refundedTotal + transitions the
  order to PARTIALLY_REFUNDED or REFUNDED at scale-2 precision.
  Emits an OrderStatusEvent for the timeline on every attempt,
  successful or failed — support can see "attempted a $40 refund; the
  gateway said DECLINED" without spelunking the log files.
- api-admin `refunds/RefundResource`: two endpoints under
  `/api/admin/v1/orders/{uuid}/refunds` — GET lists the full history,

  ORDER_MANAGER only (moving real money is more restrictive than
  reading orders). The refund list is embedded in AdminOrderDetail so

PHASE 4d.3 — Abandoned-order sweeper                           [COMPLETE]
===========================================================================
Closed a silent MVP bug: `OrderService.createFromCart` reserves inventory
on placement, but the only paths that release the reservation are the
customer's explicit cancel and the CyberSource webhook's payment-failed
callback. A customer who closes the tab on the CyberSource redirect page
fires neither, so the reservation blocks other buyers forever. Now a
scheduled sweeper expires those rows.

Backend (Quarkus, persistence + api-storefront)
-----------------------------------------------
- `CheckoutOrderRepository.listStuckSince(status, olderThan, limit)`:
  new Panache query — orders in `status` whose `placedAt` is strictly
  older than `olderThan`, oldest-first, page-limited so a fresh boot
  after a long outage doesn't try to cancel everything in one tx.
- `OrderService.findAbandonedIds(olderThan, limit)`: `@Transactional`
  read that hands back plain `List<Long>` — no entities cross the tx
  boundary, so nothing lazy can blow up in the outer sweeper loop.
- `OrderService.cancelAbandoned(orderId, reason)`:
  `@Transactional(REQUIRES_NEW)` per-order write. Re-loads the row
  inside the fresh tx, re-checks that it is still PENDING_PAYMENT
  (turning a webhook race into a no-op instead of a corrupt row),
  transitions to CANCELLED with source=SYSTEM + actorId=null, emits
  the status event, calls the existing `releaseReservedStock` helper,
  stamps `cancelledAt`, returns `true`/`false` so the caller can
  distinguish "flipped" from "lost the race".
- `AbandonedOrderSweeper` (@ApplicationScoped, quarkus-scheduler):
    - `@Scheduled(every = "${gadaa.orders.abandoned-sweeper.every:5m}",
      delay = 30s, concurrentExecution = SKIP)`. 30s startup delay so
      we never race Flyway or initial CDI init on a fresh boot.
    - AtomicBoolean re-entrancy guard on top of Quarkus's `SKIP` —
      belt & braces because a stalled DB might not honour SKIP
      instantly on all versions.
    - Reads via `findAbandonedIds`, then iterates and calls
      `cancelAbandoned` per id. Tally per run: cancelled / skipped /
      failed. Failures are logged with the order id but never crash
      the loop or the sweeper thread.
    - `runNow()` test/ops hook lets an integration test drive a
      sweep on demand; it is deliberately NOT exposed on any REST
      path.
- Config keys (application.properties in api-storefront):
    - `gadaa.orders.abandoned-sweeper.enabled=true` (env
      `GADAA_ORDERS_SWEEPER_ENABLED`)
    - `gadaa.orders.abandoned-sweeper.ttl-minutes=60` (env
      `GADAA_ORDERS_SWEEPER_TTL_MINUTES`) — CyberSource's hosted page
      typically times out at 15 min, so 60 gives us a comfortable
      margin for a slow customer who finally submits just before we
      sweep.
    - `gadaa.orders.abandoned-sweeper.batch-size=100`
    - `gadaa.orders.abandoned-sweeper.every=5m`
    - `%test.gadaa.orders.abandoned-sweeper.enabled=false` so
      integration tests that plant `PENDING_PAYMENT` fixtures with
      backdated `placed_at` never see them auto-cancelled
      mid-assertion. A specific test can flip it back on and call
      `AbandonedOrderSweeper#runNow()` explicitly.

Deferred (to a future 4d minor)
-------------------------------
- Storefront email on auto-cancel. The customer might genuinely be
  about to pay; a heads-up email ("we cancelled your unpaid order,
  reorder here") would be friendlier. The status event is the
  system of record for now; email templater lands in Phase 5.
- Admin dashboard tile showing sweeper run stats (last-run at,
  cancelled/skipped/failed counters). For now the log lines are the
  observability.
- Locking primitive for multi-instance deploys. The current sweeper
  runs on every replica; two replicas can independently call
  `cancelAbandoned(id)` on the same row — the second call is a no-op
  thanks to the status re-check, but we pay for the extra tx. Once
  we have Redis (see next section), moving the schedule under a
  ShedLock-style lease would be trivial.

------------

- The state service does not touch the Router — `archive()` takes a
  callback, and the shell decides where to navigate. This keeps the

PHASE 4d.6 — Redis rate limiter + distributed lease                [COMPLETE]
===========================================================================
Two related multi-instance holes closed in one pass:

1. `RateLimitService` was a process-local sliding window. Behind a load
   balancer with N replicas the effective quota was N × the configured
   max — an /auth/login limit of 10/min accepted 20/min on two replicas,
   30/min on three, etc. Real abuse would sail through.
2. `AbandonedOrderSweeper` used only an in-JVM `AtomicBoolean` to prevent
   overlapping runs. Two replicas would sweep in lockstep, racing on the
   same PENDING_PAYMENT rows and wasting one full sweep every cycle.

Both are now backed by a runtime-selectable strategy (memory | redis) so
single-instance dev keeps working unchanged, and prod flips a single env
var per feature to opt into shared state.

Backend (Quarkus)
-----------------
- `build.gradle`: added `io.quarkus:quarkus-redis-client`. The dep is
  always on the classpath but the client only actually connects when a
  Redis backend is opted in.
- `application.properties`:
    * `gadaa.ratelimit.backend=memory|redis` (default memory)
    * `gadaa.leases.backend=memory|redis`   (default memory)
    * `quarkus.redis.hosts` sample line (commented) + `quarkus.redis.timeout=2s`
- `infra/docker-compose.yml`: new optional `redis` service (redis:7-alpine,
  persistence off, healthcheck ping, exposes 6379) behind the `redis` and
  `app` profiles so `docker compose up mysql minio mailhog` still Just Works
  without touching Redis. The api-storefront service now also passes
  `GADAA_RATELIMIT_BACKEND` / `GADAA_LEASES_BACKEND` / `QUARKUS_REDIS_HOSTS`
  through from the shell env.

Rate limiter — pluggable strategy
---------------------------------
- `ratelimit/RateLimitBackend.java` (new): interface with
  `tryAcquire(bucket, clientId, max, window) -> Decision`, `activeKeyCount()`,
  `label()`.
- `ratelimit/InMemoryRateLimitBackend.java` (new): the pre-4d.6 sliding
  window logic extracted verbatim (ConcurrentHashMap of ArrayDeque<Long>
  per key, synchronized-on-queue for correctness, `@Scheduled` reap of
  15-min-idle keys). Behaviour identical to before.
- `ratelimit/RedisRateLimitBackend.java` (new): atomic Lua sliding window
  on a Redis ZSET.
    * Per (bucket, clientId) key at `gi:rl:<bucket>:<clientId>`, members
      = per-hit unique tokens (`<now-ms>:<seq>`), scores = now-ms.
    * Single 12-line Lua script does ZREMRANGEBYSCORE → ZCARD → early
      return with oldest score if `count >= max`, else ZADD + PEXPIRE.
    * Caches the SHA and prefers EVALSHA; on `NOSCRIPT` (Redis restarted
      or SCRIPT FLUSH'ed) transparently falls back to full EVAL and
      reloads. Preloads the script in @PostConstruct; non-fatal if Redis
      is unreachable at boot (retries on first call).
    * Fail-open on any Redis exception — a Redis outage should not take
      the site offline. The limiter is defence-in-depth, not the only
      gate (bcrypt/PBKDF2, session invalidation, etc. still apply).
    * `activeKeyCount()` returns -1 (SCAN would be O(keyspace); this
      method is diagnostic-only).
    * Uses the string-command overload of `RedisDataSource.execute`
      (`"EVAL"`, `"EVALSHA"`, `"SCRIPT" "LOAD"`, `"SET"`) so we don't
      depend on the exact layout of `io.vertx.mutiny.redis.client.Command`
      across Vert.x minor versions.
- `ratelimit/RateLimitService.java` refactored to a selector shim:
    * Reads `gadaa.ratelimit.backend` at @PostConstruct, picks memory or
      redis, logs the choice. If `redis` is requested but the bean can't
      be resolved (redis-client dep pulled out), warns and falls back to
      memory rather than failing startup.
    * `tryAcquire` signature + `Decision` record unchanged, so
      `RateLimitFilter` and every `@RateLimit` call site work as-is.
    * Added `activeBackendLabel()` for /q/health surfacing.

Distributed lease
-----------------
- `leases/LeaseToken.java` (new): immutable-ish handle (name, nonce,
  expiresAt, release closure). `release()` is idempotent — the closure
  runs at most once, so try-finally callers don't need to guard against
  double release.
- `leases/LeaseBackend.java` (new): `tryAcquire(name, ttl) -> Optional<LeaseToken>`.
- `leases/InMemoryLeaseBackend.java` (new): ConcurrentHashMap of
  currently-held tokens. Trims expired entries before deciding contention
  so a crashed-mid-run holder doesn't lock forever. Release does a
  match-and-clear on the map keyed by nonce so a stale expired token
  can't wipe a successor's lease. Sufficient for single-instance deploys.
- `leases/RedisLeaseBackend.java` (new): `SET key nonce NX PX <ttlMs>`
  for acquire; a 4-line Lua check-and-delete (`GET == nonce → DEL`) for
  release. Fail-CLOSED on acquire — returning empty when Redis errors
  means the caller skips the run, which is strictly better than every
  replica sweeping at once. Release swallows exceptions and logs; the
  TTL will drop the key eventually if the DEL fails.
- `leases/DistributedLease.java` (new): same selector-shim pattern as
  RateLimitService. Reads `gadaa.leases.backend`, injects both backends,
  picks one at @PostConstruct.

Sweeper integration
-------------------
- `order/AbandonedOrderSweeper.java`:
    * Added `LEASE_NAME = "abandoned-order-sweeper"` constant.
    * `sweep()` now: check @Scheduled SKIP + AtomicBoolean re-entrancy
      → `lease.tryAcquire(LEASE_NAME, 15min)` → if empty, DEBUG-log and
      return; if held, call `doSweep()` in a try-finally, release the
      token in the finally.
    * The 15-minute lease TTL is 3× the default `every=5m` cadence so a
      slow sweep doesn't lose the lease mid-flight. The TTL exists solely
      to auto-recover from a JVM crash mid-run.
    * `doSweep()` split out of `sweep()` — the original loop verbatim
      (find abandoned ids in a short tx, cancel each in REQUIRES_NEW,
      log counts). Structure kept identical so 4d.3's transactional
      semantics carry through unchanged.

Design invariants
-----------------
- Rate limiter: fail-OPEN (Redis dies → traffic keeps flowing). Rate
  limits are belt-and-braces defence.
- Lease: fail-CLOSED (Redis dies → sweep skipped). Overlapping sweeps
  waste more than skipping one cycle costs.
- Memory backends preserve pre-4d.6 behaviour bit-for-bit. Nothing in
  the default `docker compose up mysql minio mailhog` bring-up path
  needs Redis; setting `gadaa.ratelimit.backend=redis` without also
  running Redis produces per-call WARN logs and fail-open behaviour, so
  the failure mode is loud but non-fatal.
- Every `@RateLimit` call site (`AuthResource`, `CartResource`,
  `OrderResource`) unchanged — the annotation contract and the
  `RateLimitFilter` DTO shape survived the refactor.

Deferred (out of scope for MVP)
-------------------------------
- Sentinel / cluster Redis support. Quarkus's Redis client can be pointed
  at a Sentinel or cluster URI list — the code doesn't care, but we
  haven't tested it.
- Prometheus metrics on the two backends (rate-limit hits/rejects,
  lease acquires/skips). Wiring is straightforward given the existing
  `quarkus-micrometer-registry-prometheus` extension; deferred until
  ops actually asks for the graph.
- Redis persistence for the rate-limit ZSETs. Right now `redis-server
  --save "" --appendonly no` is intentional — restart loses the state,
  which matches the memory backend's semantics and is what we want for
  a limiter.

- Backward compatibility: all variant references are nullable. Products
  without variants work exactly as before — inventory.variant_id NULL,
  cart_item.variant_id NULL, order_item.variant_id NULL.
- Variant SKU uniqueness is global (uk_variant_sku), matching product
  SKU uniqueness. This simplifies fulfilment lookups.
- Variant inventory is separate from product inventory. A product with
  variants should have its product-level inventory set to 0 or removed;
  the storefront toDetail shows product-level inStock/availableQuantity
  for the "no variant selected" state and per-variant stock in the
  variants list.
- Cart unique constraint includes variant_id so the same product can
  appear as multiple lines (one per variant). MySQL treats NULL as
  distinct in unique constraints, so (cart=1, product=5, NULL) and
  (cart=1, product=5, variant=3) coexist.
- Price override: when variant.priceOverride is non-null, it takes
  precedence over both the product base price and the customer's
  price-list tier price. This is intentional — variant pricing is
  absolute, not a delta.
