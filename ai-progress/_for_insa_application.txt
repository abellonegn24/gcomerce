2. Background of Organization

Gadaa Istar J&M Business Group plc is an Ethiopian export company specializing in the international
trade of Ethiopian coffee (raw and processed) and specialty agricultural products, including white
products and spicy products. The company serves both B2B (wholesale) and B2C (retail) international
buyers.



To modernize and scale its export operations, Gadaa Istar has developed a custom hybrid B2B + B2C
e-commerce platform that enables international buyers to browse the product catalog, request
quotes (B2B), place orders, and pay securely through hosted payment gateways. The platform is
integrated with Mastercard Payment Gateway Services (MPGS) for PCI-DSS-compliant payment
processing.



The platform is hosted on Ethio Telecom Cloud with Cloudflare providing edge security, CDN, and TLS
termination. The application is fully owned and operated by Gadaa Istar J&M Business Group plc

6.4 Custom Development


The entire platform is custom-developed by the Gadaa Istar engineering team. Notable custom
components include:



- JWT issuer/verifier (JwtIssuer.java) — HS256 token issue + verify with audience separation
(storefront vs admin) and purpose-scoped short-lived tokens for MFA challenges.

- TOTP MFA service (TotpService.java) — self-contained RFC 6238 TOTP implementation (no third-
party TOTP library) with base32 encoding and constant-time comparison.

- Rate limiter (RateLimitService + @RateLimit annotation) — pluggable backend (in-memory
sliding window or Redis-backed Lua ZSET script) with per-endpoint bucket configuration.

- Distributed lease (LeaseTokenService) — SET NX PX + check-and-delete for the abandoned-order
sweeper across replicas.
- Payment gateway signature service — HMAC-SHA256 signed field set builder + webhook signature
verification.

- Abandoned-order sweeper — scheduled job that auto-cancels PENDING_PAYMENT orders past their
TTL and releases inventory reservations.

- Invoice numbering — gap-free, per-fiscal-year invoice sequence using SELECT ... FOR UPDATE
serialization.

- Image thumbnail generation — server-side 300px (card) and 800px (detail) variants on upload.

8. Security Functionality Document


8.1 User Roles and Access Control


Implementation: Role-based access control (RBAC) is enforced at two layers:



1. Database layer — role and permission tables with role_permission join table (Flyway V1). Five
seeded admin roles: SUPERADMIN, PRODUCT_MANAGER, ORDER_MANAGER, CUSTOMER_MANAGER, FINANCE.
2. Application layer — SecurityContextHolder (per-request, CDI @RequestScoped) populated by
JwtAuthFilter from the JWT roles claim. Endpoints call requireCustomer(), requireAdmin(), or
requireAnyRole(String...) to enforce access. requireAnyRole throws ForbiddenException
(403) if the caller lacks any of the allowed roles.



3. Frontend layer — Angular route guards (authGuard, guestGuard, roleGuard,
mfaChallengeGuard) prevent unauthorized navigation. roleGuard reads data: { roles: [...] }
from the route definition.



                            *Sample — admin endpoint with role enforcement:*




@POST

@Path("/products")

public ProductDto create(@Valid ProductDtos.CreateRequest req) {

    securityContext.requireAdmin();

    securityContext.requireAnyRole("SUPERADMIN", "PRODUCT_MANAGER");

    return productsService.create(req);

}




8.2 Authorization Mechanisms


                                           *Implementation:*




- JWT-based authorization — Every authenticated request carries Authorization: Bearer
<token>. The JwtAuthFilter validates the token (signature, issuer, audience, expiration) and
populates SecurityContextHolder.

- Audience separation — Storefront tokens (aud_type=STOREFRONT) cannot access admin endpoints
and vice versa. Path-based routing: /api/admin/* validates against the admin secret; everything else
uses the storefront secret.
- Purpose-scoped tokens — Short-lived JWTs with a purpose claim in the JOSE typ header (e.g., mfa-
challenge) prevent token reuse across flows. verifyPurpose() rejects tokens with the wrong
purpose.

- Frontend interceptor — authInterceptor attaches the Bearer token to every API call and performs
a single silent refresh on 401 before failing.



8.3 Input Validation and Sanitization


                                           *Implementation:*




- Bean Validation (JSR 380 / Jakarta Validation) — All request DTOs use @Valid + constraint
annotations (@NotBlank, @Email, @Size, @Pattern, @Min, @Max, custom validators). Quarkus
Hibernate Validator enforces these at the JAX-RS layer before the request reaches the service.

- Global exception mapper — GlobalExceptionMapper catches ConstraintViolationException
and returns a structured 400 response with per-field error details. It never leaks stack traces or
internal messages on 5xx errors.

- SQL injection prevention — All database access uses JPA/Hibernate with parameterized queries
(Panache repository methods). No raw SQL string concatenation in application code. Flyway
migrations use parameterized DDL.

- XSS prevention — Angular's default template binding ({{ }}) contextually escapes output.
innerHTML is avoided; where used, content is sanitized via Angular's DomSanitizer. Backend never
returns HTML in API responses (JSON only).

- Email normalization — All email inputs are trimmed and lowercased before DB lookup/insert to
prevent case-sensitivity bypass.



                                       *Sample — validated DTO:*




public record RegisterRequest(

    @NotBlank @Size(max = 255) @Email String email,
       @NotBlank @Size(min = 8, max = 128) String password,

       @NotBlank @Size(max = 120) String firstName,

       @NotBlank @Size(max = 120) String lastName,

       @Pattern(regexp = "B2C|B2B") String customerType,

       String companyName, String companyTin, String companyVatNumber,

       @Size(max = 64) String phone,

       String preferredCurrency, String preferredLocale, String customerGroupCode

) {}




8.4 Session Management


                                             *Implementation:*




- Access tokens — JWT HS256, 15-minute TTL (gadaa.jwt.access-ttl-minutes). Claims: sub (user
ID), iss (audience-specific issuer), aud (audience), exp, iat, jti (UUID), email, roles, aud_type.

- Refresh tokens — Rotating, 30-day TTL (gadaa.jwt.refresh-ttl-days). Stored as SHA-256 hashes
in customer_refresh_token / admin_refresh_token tables (never stored in plaintext). Each
rotation invalidates the previous token and links via replaced_by_id for audit. IP address and User-
Agent are recorded.

- Logout — Revokes the presented refresh token (sets revoked_at). On password change / reset, all
existing refresh tokens for the user are revoked.

- Token secret management — JWT secrets (GADAA_JWT_STOREFRONT_SECRET,
GADAA_JWT_ADMIN_SECRET) are loaded from environment variables in dev and from HashiCorp Vault
in staging/production. Minimum 32 characters (validated on startup).

- No server-side session state — The platform is stateless; all session state lives in the JWT. This
simplifies horizontal scaling.

- Idempotency — Order creation supports an Idempotency-Key header to prevent duplicate orders
from network retries.
8.5 Error Handling and Logging


                                           *Implementation:*




- Global exception mapper (GlobalExceptionMapper) — Single @Provider that maps every
uncaught exception to a standard error envelope (ErrorResponse with code, message, details,
correlationId, timestamp). Priorities:

 1. ApiException (domain exceptions) — respected as-is (status + code from exception).

 2. ConstraintViolationException — 400 with field-error map.

 3. JAX-RS NotFoundException — 404 ROUTE_NOT_FOUND.

 4. WebApplicationException — pass-through with generic envelope.

 5. Anything else — 500 INTERNAL_ERROR, logged with stack trace, generic message to client (no
internal leakage).

- Correlation IDs — CorrelationIdFilter attaches a UUID to every request (from X-Correlation-
Id header or generated). Written to SLF4J MDC, stored on request context, echoed back in response
header. Enables end-to-end log tracing.

- Structured logging — Production profile uses JSON console logging
(%prod.quarkus.log.console.json=true ) for log aggregation. SQL logging is disabled in
production.

- Rate limit errors — Return HTTP 429 with a Retry-After header so well-behaved clients back off.

- No sensitive data in logs — Passwords, tokens, and card data are never logged. The payment
webhook handler deliberately does not log failed signature bodies (defense against attackers spraying
malformed POSTs).

9.2 Additional Secure Coding Rules


1. Never log secrets — Passwords, JWT tokens, refresh tokens, payment gateway keys, and card data
are never written to logs. The CorrelationIdFilter ensures traceability without exposing payloads.

2. Never trust user input — All external input passes through Bean Validation before reaching service
logic. Email is normalized; IDs are typed (Long); enums are validated via @Pattern.

3. Use parameterized queries only — JPA/Hibernate + Panache repositories. No string-concatenated
SQL anywhere. Code review rejects any raw SQL.

4. Fail secure on auth — Invalid JWTs are treated as anonymous (not rejected outright) so public
endpoints work; endpoint-level requireCustomer() / requireAdmin() enforce auth where needed.
Invalid passwords return the same error as unknown emails (INVALID_CREDENTIALS) to prevent user
enumeration.

5. Idempotency for mutations — Order creation and payment webhooks support idempotency keys /
state checks to prevent duplicate processing.
6. Constant-time comparisons — TOTP verification uses constant-time comparison across the
tolerance window to prevent timing attacks.

7. No cookies for auth — Authentication uses Authorization: Bearer headers, not cookies,
eliminating CSRF risk for auth. SameSite cookie attributes are not needed because no auth cookies
are set.

8. CORS is explicit — Only the configured storefront and admin origins are allowed
(quarkus.http.cors.origins). Dev profile allows /.*/ for local development only.

9. Secrets in Vault (prod) — All secrets (JWT keys, MPGS keys, SMTP credentials, DB passwords) come
from environment variables in dev and HashiCorp Vault in staging/production. No secrets in source
code or config files.

10. Defense in depth — WAF (Cloudflare) → Nginx rate limiting → Application rate limiting → JWT
auth → RBAC → Input validation → Parameterized queries. Multiple layers must fail for an attack to
succeed.
